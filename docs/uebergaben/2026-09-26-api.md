## 4. Schnittstellen

Alle 125 Endpunkte aus `api.ts` sind registriert (automatisch geprüft in
`test/endpunkte.test.ts`). Präfix `/api/v1`, Anmeldung `Authorization: Bearer <token>`,
Fehlerformat `ApiError`. Statuscodes: Anlage 201 (bei idempotenter Wiederholung per Client-ID
200), sonst 200, ohne Inhalt 204 (Abmelden, Passwort-Endpunkte, gelesen markieren, Geräte,
Webhook). Kunden erhalten für nicht erlaubte und nicht vorhandene Objekte 404, Mitarbeiter
403 mit Begründung; Zustandskonflikte 409, fachliche Ablehnungen 422, ungültige Eingaben 400.

Öffentlich (ohne Sitzung): `login`, `acceptInvitation`, `forgotPassword`, `resetPassword`,
`health`, `resolveQr`, `publicShare`, `sumupWebhook`; WebSocket `/api/v1/realtime`
(Anmeldung über die erste Nachricht).

Wichtige Funktionen für Hintergrundläufe: `deliverPendingNotifications()`
(`src/notifications/delivery.ts`), `reconcilePendingCheckouts()` (`src/services/payments.ts`),
`notifyMaintenanceDue()` (`src/services/maintenance.ts`); alle werden in `server.ts` zyklisch
aufgerufen.

## 8. Abweichungen und Festlegungen (bitte prüfen)

Ergänzung in `packages/domain` (minimal, mit Test): `canViewMessages` und
`canViewApprovalRequest` prüfen für Kunden jetzt `canViewWorkOrder` mit. Vorher sahen Kunden
Chat und gesendete Freigabeanfragen eines Auftrags im Status `draft`, obwohl der Auftrag
selbst nach der Lead-Präzisierung unsichtbar ist.

Vertragsergänzungen (Eingaben ohne Schema in `requests.ts`, bzw. optionale Zusätze):
- `POST /work-orders?draft=true` legt einen Entwurf an; ohne Parameter entsteht der Auftrag im
  Status `open`. Freischalten per `transition` → `open`.
- `PUT /work-orders/:id/assignees` Körper `{ assigneeIds: uuid[] }`.
- `POST /documents/:id/versions` Körper `{ fileId, note? }`.
- `POST /invoices/:id/cancel` optional `{ reason? }`; `POST /appointments/:id/confirm` optional
  `{ overrideConflictsReason? }`; `…/proposals/:proposalId/decline` optional `{ cancel? }`.
- `POST /appointments/conflicts` Körper `{ id?, startsAt, endsAt, resourceId?, assigneeIds, workOrderId? }`.
- `GET/PUT /notification-preferences` Antwort in der Form von `NotificationPreferencesRequestSchema` (vollständige Matrix mit Voreinstellungen).
- `PUT /settings/workshop` Körper = `WorkshopSettings` ohne `paymentProviderConfigured`;
  Wartungsarten/Hebebühnen = DTO ohne `id` (ID aus dem Pfad, Anlage per PUT).
- PATCH-Endpunkte ändern nur übermittelte Felder (zod-Standardwerte werden bei PATCH nicht
  angewendet). `PATCH /customers/:id` akzeptiert Teilangaben; das Ergebnis wird gegen
  `CustomerInputSchema` geprüft.
- `GET /public/shares/:token`: abgelaufen/widerrufen → 410 (`share_expired`/`share_revoked`),
  unbekannt → 404.
- `FinishWorkItemRequest`: ausdrücklich `odometerKm: null` bedeutet "km-Stand unbekannt"
  (Domain `odometerUnknown`); fehlt das Feld bei einer Wartungsposition → 409 `odometer_required`.

Fachliche Festlegungen in der API:
- Nach bestätigter Annahme lehnt `POST /work-orders/:id/items` neue Positionen ab (409
  `approval_required`, R-ANN-3); Änderungen an Annahme-Inhalt oder Annahme-Positionen machen
  eine frühere Bestätigung ungültig (Audit).
- Positionen einer Freigabeanfrage entstehen erst beim Senden (keine Preise vor dem Senden im
  Auftrag); Zeile i der Version ↔ i-te Position der Anfrage. Beim Senden werden die in der
  Version genannten Fotos für den Kunden sichtbar (R-FRG-2).
- Chat-Anhänge werden als Fotos (Kontext `chat`, kundensichtbar) gespeichert; `contentUrl`
  zeigt auf die rechtegeprüfte Foto-Route. Kunden können nur selbst hochgeladene Dateien
  anhängen.
- Rechnung stellen veröffentlicht das zugehörige PDF-Dokument für den Kunden; Fälligkeit
  Standard = heute + `payment_term_days`.
- Online-Zahlung nur, wenn `workshop_settings.payment_provider = 'sumup'` und ein Anbieter
  konfiguriert ist; `PAYMENT_PROVIDER=fake` wird in Produktion abgelehnt. Mitarbeiter lösen
  keinen Online-Checkout aus (Domain `canStartCheckout`).
- Empfänger "Service" für Benachrichtigungen = aktive Konten mit Rolle admin oder service.
- QR-Scan eines berechtigten Mechanikers führt zum zuletzt geänderten, ihm zugewiesenen
  aktiven Auftrag des Fahrzeugs, sonst zu `/mechaniker`.
- Log-Mailer: vollständige Mails nur als Datei in `MAIL_LOG_DIR` (lokaler Postausgang, enthält
  Einladungs-/Rücksetzlinks), im Log nur maskierte Empfänger und Betreff.
